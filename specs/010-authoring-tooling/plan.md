# Implementation Plan: Authoring Tooling

**Branch**: `claude/modest-noether-nlycur` (spec directory `010-authoring-tooling`) | **Date**: 2026-11-21 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/010-authoring-tooling/spec.md`; decisions in ADR 0018 and ADR 0019.

## Summary

Four pieces of maintainer tooling, none of which changes what the integrity gate accepts:

1. **`registry new <family> <title>`** (US1, TCX-62) generalises the existing `registry new essay` (`src/registry/new-essay.ts`): mint with `mintNext`, write a stub at `proposed`/`held`, write the provenance checklist derived from the rules, roll back if the gate gets worse. Rules gain a small declarative `requires` list so the checklist is read from them, and a test proves the checklist and the rules agree in every family.
2. **The dependents graph** (US2, TCX-63) is one pure function over `referenceFields` (the gate's own definition of a reference), written by `registry check --out` as `dependents.json` and `dependents.html` beside `integrity-report.json`, and queried by `registry deps <id>`.
3. **Editor schemas** (US3, TCX-61) are generated by a script from the Zod family schemas with `z.toJSONSchema`, overlaid with the vocabularies (from the `*_VALUES` constants and their `GLOSSARY.md` definitions) and ID suggestions, written to an ignored `.schemas/` directory on `postinstall`, `predev` and `prebuild`, and wired to VS Code's YAML extension by a committed `.vscode/settings.json`.
4. **The link and manifest checker** (US4, TCX-64) is a standalone script with injected `fetch`, Jira and GitHub clients, run by a new weekly workflow. It never runs in `registry check` or `npm run build`.

## Technical Context

**Language/Version**: TypeScript (strict) on Node ≥ 24, as the rest of the registry; run through `tsx`.
**Primary Dependencies**: existing only: `zod` 4 (`z.toJSONSchema`), `yaml`, Node's `fetch` and `node:util` `parseArgs`. No new runtime dependency; one devDependency, `ajv`, so the editor-schema test can validate records against the generated schemas (T032). CI uses `actions/cache` and `actions/checkout`, already in use.
**Storage**: files. Records under `content/`; generated schemas under `.schemas/` (ignored); graph and report under the `--out` directory (CI artefact); manifest fingerprints in the link-check workflow's cache.
**Testing**: Vitest, with valid and invalid fixtures (Principle X). Network, Jira, GitHub and the web archive are injected interfaces with in-memory stand-ins; no test touches the network.
**Target Platform**: the maintainer's machine (VS Code with the Red Hat YAML extension) and GitHub Actions `ubuntu-latest`.
**Project Type**: CLI and build tooling inside the existing single project.
**Performance Goals**: `registry deps <id>` answers in under 5 s on the current registry (311 entities) (SC-004); the graph adds under 1 s to `registry check`; schema generation under 10 s so `predev` stays unnoticed.
**Constraints**: the gate and the build make no network request (ADR 0006 item 17, SC-008); no automation writes a record (the checker opens issues and pull requests only); held records may appear in the graph and the schemas, which are never deployed, but never in `dist/` (the leak scan already covers `dist/`).
**Scale/Scope**: 15 families, 14 scaffoldable; 311 entities today; on the order of a few hundred external URLs.

## Constitution Check

*GATE: must pass before Phase 0 research. Re-checked after Phase 1 design (below).*

- [x] **I. Historical question.** Stated in the spec: *how can one maintainer keep every claim traceable to its evidence as the registry grows, without loosening the rules that make it traceable?* The tooling adds no reader-facing feature, so no new historical claim is made.
- [x] **II, V. No duplicated records or private geometry.** The scaffold writes one canonical record per ID and never copies a description; the graph and the schemas are derived and uncommitted; IDs are minted by the one minter (ADR 0006), and R calls it rather than reimplementing it.
- [x] **III, VI. Uncertainty and provenance as fields.** The stub writes `pending` and `unknown` as values and leaves the fields that need a person as commented keys, so nothing is guessed at creation. A dead link never changes `verified` (FR-016); an archived copy is a new pair of fields, proposed and merged by a person (FR-018).
- [x] **IV. Interactions.** None: the dependents viewer is an editor artefact, not deployed, and has no evidentiary claim to make.
- [x] **VII. No dynamic infrastructure.** A scheduled GitHub Actions workflow is CI, not runtime infrastructure; nothing is added to the published site.
- [x] **IX. Accessibility and performance.** No change to any deployed page. The static viewer is built to the same standards as the integrity report's HTML (`report-html.ts`: semantic table, no script required), but it is not held to the ADR 0004 budgets because it is never served.
- [x] **X. Test strategy.** Every acceptance scenario maps to a test written first; the map is in [quickstart.md](quickstart.md) and becomes the task list.

**Result: PASS.** No violation, so Complexity Tracking is empty.

**Re-check after Phase 1:** PASS. The design added two things worth checking against the constitution. (a) Rules declare the fields they require (`requires`): this moves no rule and weakens none; SC-003's test compares every rule's ID and threshold before and after. (b) Vocabulary values get definitions in `GLOSSARY.md` (research R4): this is the glossary's job, and the values already live in ADR 0003; no value is added or removed.

**Structure decision**: everything stays in the existing single project. The checker lives in its own `src/linkcheck/` so that a test can assert nothing under `src/registry/`, `src/pages/` or `scripts/` used by the build imports it (SC-008).

## Delivery

Four pull requests, one per story, in priority order: US1 (TCX-62), then US2 (TCX-63), then US3 (TCX-61), then US4 (TCX-64). US2, US3 and US4 do not depend on US1 or on each other; US2 and US3 may swap. US4 adds the locator's `archived_copy` and `archived_on` itself (T042, T043). Each PR updates `docs/confluence/build-log-spec-010.md`, `GLOSSARY.md` where a term is added, the spec 001 rule table and data model where they change, and the status blocks.
